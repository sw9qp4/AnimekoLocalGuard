## E.2 路线 A：先做"无模型也能用"的规则基线（**我推荐**）

### 核心想法

当前设计直接跳向"模型判断这条弹幕是否涉及某事实"。
但一个更简单、可验证、当天就能用的基线是：

```
弹幕文本
   │
   ├── 1. 实体别名匹配：是否提到 knowledge pack 里的某个实体/别名？
   │      （pack 里已经有 entities + aliases + ambiguousAliases）
   │
   ├── 2. 事实关键词匹配：是否命中该事实的显式关键词集合？
   │
   └── 3. 严重程度 + 时间线：如果涉及的是尚未揭晓的事实 → 拦
```

### 为什么可能更好

| 优点 | 说明 |
|---|---|
| 立即可用 | 不需要训练、不需要下载模型 |
| **可解释** | 每条拦截都能说明"因为提到了 X，而 X 在第 N 集才揭晓" |
| 可调试 | 误拦/漏拦都能直接定位到规则 |
| 可测量 | 能人工标注几十条真实弹幕，**立刻**验证阈值方向 |
| 为模型提供基线 | 将来接模型时，有对照物才知道模型是否真的更好 |
| 暴露真实问题 | 会立刻暴露"别名歧义""实体在揭晓前就被提到"等真实难题 |

### 缺点

- 挡不住 D-1 里那种"不含实体名"的含蓄剧透（`"有老虚，不可能治愈"`）
- 需要人工维护关键词

### 与现有代码的关系

**几乎不需要改判定引擎**——只需要实现一个 `semanticsProvider`：

```kotlin
// 现有接口已经支持："分析失败要上报"、"不得跑在 UI 线程"、可取消
semanticsProvider = { text, factIds, episodeNumber ->
    DanmakuSemantics(
        scores = mapOf(GuardCategory.SPOILER_EXPLICIT to score),
        factIds = matchedFactIds,
        analyzerVersion = ...,
    )
}
```

### 需要人决定

- 是否接受"先做规则、后做模型"的顺序？
- 关键词由谁维护？（可以由我从声明文件里推导一部分，但事实关键词应人工确认）

## E.3 路线 B：直接做模型（G3 原计划）

### 需要回答的问题

1. **10M–50M 参数的编码器做"是否涉及某事实"判定，现实吗？**
   这个任务实际是**多标签分类**（对每条事实判断"是否涉及"），
   输入是短文本（多数弹幕 < 20 字），标签数 = 该作品的事实数（可能 5–30 个）。
   - 这个规模下，一个小的中文编码器 + 分类头**也许可行**
   - 但**训练数据从哪来**？需要标注"这条弹幕是否涉及事实 F"。
     没有标注数据，就不能训练。
2. **能不能用现成的小模型而非自己训练？**
   任务说明限制"不训练大模型、不大量下载"，但没禁止使用已有的小模型。
3. **是否需要模型？** 也许规则 + 别名词典能覆盖 80% 的情况。

### 我的判断（可能错）

在没有标注数据之前，**路线的瓶颈不是模型大小，是数据**。
所以建议先走 A，用 A 跑一批真实弹幕，**顺手产出标注数据**，再决定是否训练。

## E.7 三个"如果……就……"的止损条件

诚实地说，有些情况应该**重新考虑项目方向**而不是继续投入：

1. **如果**真实弹幕里符合"可判定为剧透"的样本比例极低（比如 < 1%），
   **那么**这个功能的价值可能不足以支撑其复杂度——应该先用第二步的数据测量这个比例。

2. **如果**规则基线在真实弹幕上的误拦率很高（把正常讨论当成剧透），
   **那么**用户会直接关掉它，功能等于不存在。误拦率是需要**优先测量**的指标，
   比"拦住了多少剧透"更重要。

3. **如果** DanDanPlay 拿不到凭据，且自有源覆盖率始终是个位数，
   **那么**整个"弹幕过滤"在实际使用中无事可做——这种情况下应该先解决数据源问题，
   而不是继续完善过滤逻辑。
