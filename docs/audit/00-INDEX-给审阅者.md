## 请先读这一段

这份材料的写法与常规"项目汇报"不同，原因如下：

1. **我把已知问题放在最前面**（`D-GAPS-AND-RISKS.md`），而不是放在最后。
   如果时间有限，**只读 D 文件**就够形成判断。
2. **所有状态词严格区分**：`IMPLEMENTED` / `UNIT_TESTED` / `BUILT` / `DEVICE_VERIFIED`
   是四件不同的事。本项目**没有任何一项达到 `DEVICE_VERIFIED`**。
3. **`BUILT` 只代表编译打包成功**，不代表能播放，也不代表功能生效。
4. **411 个测试全部使用虚构数据**，证明逻辑自洽，**不证明**对真实作品判断正确。
5. **当前打开功能开关不会屏蔽任何弹幕**——因为既没有剧情包，也没有语义模型。
   这是设计上的现实，不是 bug，但必须说清楚。

## 与常规弹幕过滤的区别（如果想快速理解它的价值）

普通关键词过滤挡不住这类弹幕（实测样本，来自魔法少女小圆第 1 集）：

> `"有老虚，不可能治愈"`

这句话没有任何敏感词，但它把整部作品的**预期**改掉了。它是不是剧透，只取决于
**观众此刻应该已经知道多少** —— 这是时序判断，需要三样输入：

```
(这条弹幕说了什么) × (现在播到哪里) × (此时观众理应已经知道什么)
                                        └── 靠"人工声明的事实 + 带时间字幕推导的揭晓时刻"
```

设计上最关键的一条约束：**用揭晓时间的上界来解锁**。
早解锁 = 本该拦住的弹幕被放行，这个方向的错误不可接受；晚解锁只是多拦几条。

## 我最想要外部意见的 7 个问题

（详见 `D-GAPS-AND-RISKS.md` 第 D-16 节）

1. **资料缺失时应该放行还是拦截？**（当前是放行，与"宁可保守"原则冲突，见 D-2）
2. **阈值该怎么定？** 绝对分数 vs 相对排序+每集配额，哪个更稳健？（见 D-3）
3. **10M–50M 参数模型做"是否涉及某事实"判定现实吗？** 是否应先做规则基线？（见 D-8）
4. **"可复现构建"对 Android 是否应该要求字节级？**（见 D-4）
5. **是否应优先接入上游已有但未使用的 `shift` 字段**，而不是继续靠人工对齐？（见 D-12）
6. **用"台词引用"作为唯一证据锚是否足够？**（见 C.4）有没有更好的可复核方案？
7. **有没有我完全没想到的失效模式或攻击面？**

## 审阅时请注意三个"陷阱"

1. **不要被测试数量误导。** 292 个用例全部是虚构数据。
   它们证明逻辑自洽，不证明效果。
2. **不要被"构建成功"误导。** 本项目所有 APK 都只是 `BUILT`。
   项目历史上出现过 5 次"代码写了、测试过了，但根本没接线"，
   其中 2 次是靠死代码审计才发现的。
3. **不要假设真机验证过。** 一次都没有。设备未连接。
