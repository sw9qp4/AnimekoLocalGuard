## H.1 审阅者指出、经核实**成立**的问题

### H-1 【已修】未核对的事实在跨集后被自动解锁 —— **确认成立**

**审阅意见：** 当前时间评估器在跨到后续集数时，会先按数字比较解锁，再检查同集的可信状态；
对于尚未核对的揭晓集序，需要补充独立限制。

**核对方式：** 读 `DanmakuGuardEngine.kt` 的 `TimelineEvaluator.evaluate`。

原实现的分支顺序是：

```
1) neverUnlocksInScope → 锁定
2) 位置集 > 揭晓集 → **直接返回 unlocked = true**      ← 问题在这里
3) 位置集 < 揭晓集 → FutureEpisode
4) 同集：先检查 verification.trustedForUnlock，再比时间
```

于是第 4 步的核对门槛被第 2 步绕过：一条 `AI_CANDIDATE`（AI 生成、无人核对）的事实，
**只要播放到它声称的揭晓集之后就会被解锁**。

这与本模块自己的文档直接冲突——`StoryKnowledge.kt` 的约束写着：

> 未核对项不得作为高可信依据自动解锁。

**性质：** 这是缺陷，不是取舍。阶段二的注释把核对检查写在跨集分支之后，属于实现疏漏。

**修复：** 把核对检查提到**任何分支之前**，使其成为解锁的前置条件。

**副作用（必须记录）：** 一条"核对状态不足"的事实现在会在整个覆盖范围内持续被保护，
**即使那一集早已播完**。两个方向都有代价，本项目一律选择"宁可保守，不可提前解锁"：

| 选择 | 代价 |
|---|---|
| 要求核对 | 时间核对不了 / 未核对的事实，其所在集会持续被屏蔽 |
| 不要求核对 | 错误或存疑的事实会解锁本不该解锁的弹幕 |

若将来认为前者不可接受，正确解法是让生成流程把这类事实核对到 `VERIFIED`
（或补上可定位的时间证据），而**不是**放宽这条前置检查。

**新增测试：**
- `crossEpisodeUnlockStillRequiresTrustedVerification`（三档全覆盖）
- `unverifiedFactIsNeverUnlockedEvenInLaterEpisodes`
- `verifiedFactStillUnlocksInLaterEpisodes`（保证没把正常路径堵死）

### H-2 【已修】多事实判定结果依赖事实列表顺序 —— **确认成立**

**审阅意见：** `DanmakuGuardEngine` 最后主要使用**第一个**未解锁事实的原因决定是否降级放行，
因此信息相同、顺序不同会得出相反结论。

**核对方式：** 读 `DanmakuGuardEngine.decide` 的 `for (factId in semantics.factIds)` 循环。

原实现：

```kotlin
var firstReason: SpoilerBlockReason? = null
for (factId in semantics.factIds) {
    val eval = timeline.evaluate(...)
    if (!eval.unlocked) { sawAnyLocked = true; if (firstReason == null) firstReason = eval.reason }
}
val reason = firstReason ?: TimingUnknown     // ← 只取第一个
if (reason == TimingUnknown) { if (score < unknownFactFloor) return Visible }   // ← 可能放行
```

**反例已逐字复算并确认**（均衡档：explicit 阈值 0.60、unknownFactFloor 0.80、分数 0.70）：

| 事实顺序 | 取到的 reason | 结果 |
|---|---|---|
| 时间未知 → 未来集 | `TimingUnknown` | 0.70 < 0.80 → **放行** |
| 未来集 → 时间未知 | `FutureEpisode` | 落入确定性分支 → **屏蔽** |

**性质：** 缺陷。事实列表顺序不是信息，判定结果不得依赖它。

**修复：** 改为**逐项独立判断后合并**，且合并规则保证"增加事实只会更保守"：

1. 任一事实**确定**未解锁（未来集 / 永不解锁 / 本集未到揭晓点）→ 屏蔽；
   一个"时间未知"的事实**不得**抵消另一个"已确认属于未来集"的事实。
2. 其余情形：所有不确定事实**每一个**都允许按档位降级放行，才放行（取"最严"而非"第一个"）。

上报原因也改为确定性选择（固定优先级，不依赖遍历顺序），避免同样的输入给出不同诊断。

**新增测试：**
- `uncertainFactCannotCancelADefinitelyLockedFact`（审阅者给出的反例）
- `decisionIsIndependentOfFactOrderForEveryPermutation`（3 个事实的**全部 6 种排列**）
- `addingABlockingFactNeverTurnsBlockedIntoVisible`（3 档 × 4 个分数）

### H-3 【已修】集数变成未知时沿用上一集 —— **确认成立**（本轮最严重的一处）

**审阅意见：** 同步函数遇到 `episodeNumber == null` 直接返回，**没有清除会话里的旧集数**，
于是"界面已知道无法映射，过滤器仍按上一集判断"。

**核对方式：** 读 `EpisodeViewModel.syncLocalGuardEpisode`。

```kotlin
private fun syncLocalGuardEpisode(episodeNumber: Double?) {
    if (episodeNumber == null) return      // ← 什么都不做，旧集数留在会话里
    ...
}
```

原注释自称"the session treats 'episode unknown' as 'do not guess' rather than reusing the
previous episode"——**这句话是错的**：会话根本没有被通知，它继续持有上一集的集数。
注释描述的是意图，不是行为。

**性质：** 缺陷，且方向危险。旧进度可能让**未来事实**被当成"已经揭晓"，从而**放行**。
这比"没有过滤"更糟，因为它看起来像是在工作。

**修复：** 新增 `DanmakuGuardSession.markEpisodeUnknown()`，明确清除集数并递增生成号
（使在途旧结论失效）。调用方在无法映射时调用它。

**新增测试：**
- `unknownEpisodeClearsThePreviousEpisodeInsteadOfReusingIt`
- `repeatedUnknownEpisodeIsIdempotent`

### H-4 【已修】剧情包异步加载完成后没有绑定到会话 —— **确认成立**

**审阅意见：** 加载是异步的；完成后主要更新外部字段，而会话同步只在"集数变化"时执行，
因此存在"先识别集数 → 会话启动 → 资料加载完成 → 集数未变 → 会话仍无资料"的顺序。

**核对方式：** 读 `EpisodeViewModel` 的 `ensureLocalGuardKnowledgeLoaded` /
`loadLocalGuardKnowledge` / `syncLocalGuardEpisode`。

- 会话构造处 `knowledge = null`（构造时资料必然还没加载）
- `loadLocalGuardKnowledge()` 只写 `localGuardKnowledge` / `localGuardAlignment` 两个字段
- `syncLocalGuardEpisode` 只在该字段与已同步值不同时触发

**结论成立：** 资料加载完成时集数通常**没有变化**，因此 `startEpisode` 不会被再次调用，
会话永久持有 null 包。**"文件加载成功"≠"过滤真的用上了这个文件"。**

**修复：** 新增 `DanmakuGuardSession.updateKnowledge(knowledge, alignment)`：
不切集、不重置计数、不递增生成号（本集尚未结束，统计应连续），
但资料变化时**清事实关系缓存**（缓存键绑定资料版本）。加载完成后立即调用它。

**新增测试：**
- `knowledgeLoadedLaterIsBoundWithoutChangingEpisode`
- `decisionActuallyUsesKnowledgeThatArrivesLate`（资料到达后判定**真的**按资料执行）
- `repeatedKnowledgeUpdateIsIdempotent`

**我的独立核对：** 重新读了总任务说明，发现我原先的判断（D-2）**描述得不准确**。

**实际缺陷：** 原代码在**语义解析返回 null** 时放行。而"拿不到语义结论"= 这条弹幕

## H.2 审阅者指出、经核实**成立且尚未修复**的问题

### H-6 【列表侧已修 / 覆盖层侧未修】配置与进度变化不会触发重新审核

**审阅意见：** `allDanmakuListFlow` 主要监听弹幕列表与用户标识；过滤时读取了当前开关和
播放位置，但**没有把这些变化本身作为重新计算的触发条件**。

**核对方式：** 读 `EpisodeViewModel.allDanmakuListFlow`。

```kotlin
val allDanmakuListFlow = combine(
    episodeDanmakuLoader.allDanmakuFlow,
    danmakuRepository.selfId,
) { danmakuList, selfId -> ... }        // ← 只有这两个上游流
```

`combine` 的输入里**没有**配置流，也**没有**播放位置流；函数体内却读取了
`localGuardConfigSource.current.enabled` 和 `player.currentPositionMillis.value`。
**读取一个值不等于依赖它**——这两个值变化不会触发重新计算。结论成立。

#### 列表侧：已修

三处改动：

1. **配置成为输入。** 新增 `localGuardConfig: StateFlow<GuardUserConfig>`，
   并把它合并进 `combine`。配置**必须**有自己的输入，不能只靠位置采样——
   因为用户可以在**暂停时**打开开关，此时永远不会有位置采样到达。
2. **位置成为输入。** 用上游已有的 `sampleWithInitial`（本项目此前用它做 OP/ED 跳过）
   以 5 秒粒度采样位置。列表的可见集合是位置的**阶跃函数**：条目只会在播放跨过某条事实的
   揭晓时刻时由隐藏变为显示，因此不需要逐帧重算，只需要"位置移动足够多以至于答案可能不同"时重算。
   **5 秒是刻意的取舍**：各档余量是 0/15/30 秒，所以新解锁的条目最多晚 5 秒出现；
   但**绝不会提前出现**，因为判定用的始终是**真实**当前位置而不是采样值。晚是安全方向。
3. **判定用真实位置。** 采样只决定*何时*重算，不决定*答案*。

#### 顺带修掉一个同类问题：状态行的资料状态不会刷新

`localGuardStatusFlow` 的输入是"配置 + 计数 + 集数"。H-4 修复后资料会被推送到会话，
但这三个信号都不会因资料到达而改变 ⇒ **状态行会继续显示"资料缺失"**。
一条谎报资料是否加载的状态行比没有状态行更糟——用户会去排查一个已经解决的问题。

已新增 `localGuardKnowledgeVersion`（资料实际变化时递增）并纳入状态流。

#### 覆盖层侧：**未修**，且原因要说清楚

覆盖层 `uiDanmakuEventFlow` 对流经的每个事件判定一次，不缓存决定。所以：

- **正常播放**：新事件不断到达，档位与位置都按当前值判定 → 没有问题；
- **拖动进度**：上游会重新发送 `Repopulate`（携带事件自身的 `playTimeMillis`）→ 会重新判定；
- **真正未覆盖的情形**：弹幕已经交给显示层、用户此时**切换开关或档位**。
  已经放行的条目不会追溯隐藏，已经拦下的也不会追溯显示。

这一条**未修**的原因：修复需要在上游侧触发一次重新填充（`requestRepopulate` 之类的路径，
本轮**未核实具体 API**），而那会在播放中插入一次行为变化。
在**没有设备**的情况下，我无法判断它会不会造成画面跳动或闪烁。
所以：**先记录，不猜着改。** 需要设备与真实弹幕才能安全地做这一步。

**同类风险（审阅者也提到，仍未验证）：** 切换片源后旧的对齐与已排队事件是否失效。

### H-7 【未修】对齐只按作品绑定，且误差边界没有进入运行时

**审阅意见（两点）：**
1. 对齐文件目前主要按 `workId` 读取，没有充分绑定**剧集**与实际**视频版本**；
2. 对齐生成器用 90 分位残差接受整体偏移，但生成的映射**没有把实际残差带入运行时误差边界**，
   而数据结构把默认误差设为零。

**核对方式：**
- `TextStoryKnowledgeSource` 的路径是 `story/<workId>.alignment.json` —— 按作品，**不按集**。**成立。**
- `AlignmentResolver.toBaseline` 在 `ConstantOffset` 上会应用 `errorMillis`（有测试
  `constantOffsetErrorShiftsConservatively`），但**生成器是否写入非零误差**需要再核对。**部分成立，待核实。**

**审阅者的假设例子值得记录：**
> 100 个配对点中 91 个偏移为 0，另外 9 个所在区段存在 60 秒差异。
> 90 分位残差仍可能是 0，但不能由此推出那 9 个点附近也可靠。若这些点恰好在揭晓场景，
> 错误就可能表现为**提前一分钟解锁**。

**结论：** "90 分位适合描述整体拟合质量，不足以单独证明每个剧情区段都安全"——
这个判断我认为成立，且**是本项目没有考虑到的角度**。

**未修的原因：** 需要扩展 `TimeAlignment` 数据结构（有效区段、区段误差、未覆盖区段、
视频版本绑定）。属于设计变更，不应在未想清楚前仓促改。

**这个批评完全成立。** 我在 `D-GAPS-AND-RISKS.md` 与 `A-FACTS.md` 里用"共删除 5 行，
均为空行或参数列表重排"来支撑"没有改变上游语义"，这是一个**无效论证**：

- 我在 `EpisodeViewModel` 里**新增**了 `if (!enabled) ... else ...` 分支——这是行为改变；
- 新增的守卫调用本身也是行为改变（即使开关默认关闭）。

正确表述应为：**上游既有逻辑没有被删除；但新增分支会在开关打开时改变行为，
默认关闭时行为与上游一致。** 该结论需要回归测试支撑，而不是行数统计。

**已修正 `A-FACTS.md` 与 `D-GAPS-AND-RISKS.md` 中的措辞。**

### H-10 【不成立】"缺字幕 = 无法拦截任何东西"是过强的阻塞表述

**审阅意见：** 报告把"缺字幕"多次表述为根本阻塞，这不符合模块拆分。不需要真实字幕即可完成：
核验独立包名与安装、显示前固定规则拦截、通用低俗/攻击分类、明显提前暗示的通用分类。

**这个批评成立，我的表述过强。** 准确说法应是：

| 工作 | 是否必须先有真实剧情字幕 |
|---|---|
| 核验独立包名与安装 | 不需要 |
| 显示前规则拦截 | 不需要 |
| 通用分类（低俗 / 攻击 / 明显暗示） | 不需要 |
| 某部番的**分钟级事实**判断 | 需要可靠的时间证据 |

"缺字幕"阻塞的是**分钟级事实判断**，不是整个项目。

**另外，我关于字幕的表述也应修正：** 准确说法是
"开发环境目前没有取得合适字幕，**已检查的接口**没有提供它"，
而不是"本机不可获取"——后者暗示已经穷尽所有途径，而实际上没有。

### H-11 【不成立】"自有弹幕源覆盖率低 ⇒ 项目没价值"是错误推论

**审阅意见：** 报告测的是某个自有源的抽样，而 DanDanPlay 是**未配置、未测量**，
不是整个应用都没有弹幕。

**成立。** 原始数据只说明"Animeko 自有源覆盖率低"与"DanDanPlay 未测量"。
把两者合并成"真实使用中弹幕很少"是超出证据的推论。已修正措辞。

### H-12 【采纳】两条"止损条件"不成立

**审阅意见 A：** "剧透比例低于 1% 可能不值得做"没有考虑剧透造成的损失。
一集 2000 条中 0.5% 仍是 10 条；哪怕只泄露一次重大身份或结局也可能影响观看。

**采纳。** 应评估的是"**每集漏出多少、其中多少是重大剧透、以及为避免它们删除了多少正常讨论**"，
而不是全体弹幕中的百分比。

**审阅意见 B：** "误杀比拦住多少剧透更重要"不能作为所有档位的共同原则——
严格档误杀较高、宽松档允许部分漏判是既定取舍，应**分别评价三个档位**。

**采纳。** 用统一标准否决严格模式是错的。

---

### H-13 【采纳】关于 `shift` 字段：不应直接接进剧情时间轴

**审阅意见：** `shift` 表达的是弹幕应提前/延后显示多少秒；而剧情知识库需要的是
"实际视频时间 → 基准剧情时间"的映射。**弹幕同步了不代表知识库时间也同步了。**

**采纳，我原来的建议（D-12）把两类时间混为一谈。** 修正后的立场：

- 支持研究并利用 `shift` 改善**弹幕同步**；
- **不支持**把它自动升级为"已验证的剧情对齐来源"，更不能据此取代视频版本映射；
- 即使都只是常量偏移，也必须验证方向，不能把数值原样搬过去。

---

### H-14 【采纳】以台词引用作为唯一证据锚不够

**审阅意见：** 引用能帮助定位，不能独立证明"观众此时已经知道这个事实"——
台词可能是猜测、谎言、梦境、误导或伏笔；关键揭晓也可能完全发生在画面中。

**采纳。** 每个关键事实至少应保存：作品与版本、素材摘要、字幕条目或画面位置、时间区间、
事实命题、证据如何支持它、核对状态。

同时审阅者澄清了一个我表述不清的点：**哈希证明文件身份与完整性，不证明剧情解释正确**；
但"人工写下时间码"也不必然凭感觉——**有对应素材和明确核对记录的时间码可以是有效证据**。
