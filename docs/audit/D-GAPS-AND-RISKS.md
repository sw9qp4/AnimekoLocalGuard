## D-1 【P0，已修但未验证】release 变体的包名会与官方 Animeko 冲突

### 现象

debug 变体通过 `ani.android.debug.applicationIdSuffix` 得到 `.localguard` 后缀，
得到 `me.him188.ani.localguard`。

但 **release 变体的后缀没有被设置**，因此 release 构建的 APK 包名是上游的
**`me.him188.ani`** —— 与官方 Animeko **完全相同**。

这是实测发现的，不是推测：

```
node tools/apk_inspect.js app/android/build/outputs/apk/default/release/android-default-arm64-v8a-release.apk
  → "package": "me.him188.ani"      ← 冲突
```

而同一命令对 debug APK 输出 `me.him188.ani.localguard`。

### 为什么严重

1. 安装 release 版会尝试**替换官方 Animeko**。
2. 由于两者签名不同，Android 会**拒绝安装**（`INSTALL_FAILED_UPDATE_INCOMPATIBLE`），
   所以不会真的破坏用户数据——**这一点是运气好，不是设计**。
3. 但真正危险的是**第二条路径**：如果用户先卸载官方 Animeko，release 版就能装上，
   而用户会以为自己装的是官方版。签名不同意味着它**永远不会**收到官方更新。

### 修复状态

已修改 `app/android/build.gradle.kts` 的 `release` 块，改为读取
`ani.android.release.applicationIdSuffix`，并在 `local.properties` 中设为 `.localguard`。

**但修复后未重新构建验证。** 修复过程中构建环境被破坏（见 D-10），
release APK 已被删除。**这一条在重新构建并用 `apk_inspect.js` 核对之前，应视为未修复。**

### 请审阅者判断

- 用 `local.properties` 承载后缀是否合适？（当前行为：**如果这个属性没设置，release 会静默使用上游包名**。是否应该给它一个硬编码的安全默认值，或直接让构建失败？）
- 是否应该在构建脚本里加一条断言，包名为 `me.him188.ani` 时直接报错？

## D-2 【P0，设计取舍】资料缺失/集数未知时的 fail-open 行为

### 现状

`DanmakuGuardSession.shouldDisplay`：

```kotlin
if (episodeNumber == null || pack == null) {
    bump { it.copy(bypassedNoKnowledge = it.bypassedNoKnowledge + 1) }
    return true      // ← 放行
}
```

即：**用户打开了开关，但资料缺失或集数未知时，弹幕全部照常显示。**

### 为什么这是问题

整个项目的核心原则写在多处注释里：

> 宁可保守，不可提前解锁。
> 所有取舍都朝同一方向：早解锁 = 本该拦住的弹幕被放行，这个错误的代价不可接受。

而这里的方向**相反**。后果是：用户打开开关 → 看到界面上写着"本地过滤：资料缺失" →
但**如果用户没注意读那一行**，他会以为自己在受保护，实际上一条也没拦。

### 现有的缓解

- 状态行如实显示"降级：资料缺失 / 集序未知"
- 统计里 `bypassedNoKnowledge` 单独计数，可在诊断明细里看到

### 但我认为缓解不充分

因为"状态行写了"依赖用户去读。而 fail-open 的失败模式是**静默失效**。

### 备选方案（请审阅者判断）

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 保持 fail-open（现状） | 不会误伤；用户不会被无故屏蔽 | 静默失效，与核心原则冲突 |
| B. 改为 fail-closed（资料缺失时全拦） | 绝不静默失效 | 用户会觉得"开了就什么都看不到"，体验极差；且没有资料时全拦等于让功能不可用 |
| C. **分档位处理**：严格档 fail-closed，宽松/均衡 fail-open | 让最在意剧透的用户得到真保护 | 行为更复杂，需要更多测试 |
| D. 资料缺失时**禁止打开开关**（或打开后立即回弹并提示） | 消除"以为受保护"的可能 | 用户无法预先打开开关等待资料加载 |

**我倾向 A + 更显眼的提示，但没有把握，希望你给出判断。**
这是一个产品决策，不是纯技术问题。

## D-4 【P1，未验证】没有字节级可复现性证据

G0 要求"可复现基线构建"。当前能做到：

- ✅ 构建命令固定（`tools/build_android.ps1`）
- ✅ 工具链版本锁定（Gradle 9.3.1 / Kotlin 2.4.10 / AGP 9.1.1 / JDK 21）
- ✅ 上游提交锁定
- ❌ **没有验证过两次构建产出相同字节**

### 并且有一条错误结论需要纠正

早期记录曾声称两个 APK"字节完全相同"。**该结论是错的**——
当时的比对用了 `.NET ZipArchiveEntry.Crc32`，而它对 ZIP64 条目返回不可靠的值
（实测两个大小不同的条目报出相同 CRC32）。正确方法是按条目取出字节后比 SHA-256。

目前已记录：**没有任何构建字节级可复现的证据**，且 DEX 在各次构建间存在正常差异。

### 请审阅者判断

- 对 Android 项目，字节级可复现是否现实？（DEX 顺序、时间戳、签名块的随机性）
- 如果不现实，G0 的"可复现"是否应该降级为"可重复执行 + 产物可核验（包名/签名/资产清单）"？

## D-10 【P2，已发生】构建环境被破坏（当前状态）

### 发生了什么

为了让 release 变体也带独立包名，我修改了 `app/android/build.gradle.kts`。
改完后构建报 `Unresolved reference 'plugins'`（Kotlin DSL 脚本编译错误）。

按项目历史记录，这类错误的处理方式是清 `.gradle` / `.kotlin` / `<module>/build`。
但**清完之后错误依然存在**，于是我继续清理了：

- `build-logic/build`
- `.tools/gradle-home/caches/9.3.1/kotlin-dsl`
- `.tools/gradle-home/caches/9.3.1/dependencies-accessors`
- 最终清空了整个 `.tools/gradle-home/caches`

在这个过程中报错从 `app/android/build.gradle.kts` 变成了 `settings.gradle.kts`
（`maven(String)` 解析失败），说明问题在 Kotlin DSL 的脚本编译类路径，不是我的改动。

**需要说明的是：把 `release` 块改回去、错误依然存在**，所以**不是我的改动导致的**。

### 当前状态（已实测）

- 清缓存后，`gradle :help`（完整配置）**BUILD SUCCESSFUL in 18m 32s**
- 之后 `:danmaku:localguard:testAndroidHostTest` **BUILD SUCCESSFUL，292/292 通过**

**因此构建环境已恢复。** 但：

- `artifacts/` 里的 debug APK **不包含**最新的集序适配改动（构建于该改动之前）
- release APK 已被删除，**未重新构建**

### 教训

清理 Gradle 全局缓存是**过重的手段**。正确顺序应该是：

1. 先只清项目级 `.gradle` / `.kotlin`
2. 再清 `build-logic/build`
3. 只有在确认需要时才清 `GRADLE_USER_HOME/caches` 下的**特定子目录**，
   **绝不要清整个 `caches`**（会丢掉 `gradle.properties` 之外的大量状态，
   且恢复需要重新下载依赖）

## D-12 【P2，未使用】上游有个现成的每源偏移字段被忽略了

`DandanplayEpisode.shift`（`danmaku/dandanplay/.../data/MatchVideo.kt:74`）注释写明：

> 弹幕偏移时间（弹幕应延迟多少秒出现）。此数字为负数时表示弹幕应提前多少秒出现。

**上游从不使用它**，本项目也没接。

这个字段解决的正是 `TimeAlignment` 面对的问题（不同片源的弹幕时间轴偏移），
而且它是**数据源直接给出的**，比我们靠配对字幕推算更可靠。

### 建议

在实现 `TimeAlignment` 的自动获取时，应**优先**接入这个字段，
把它作为 `ConstantOffset` 的一个来源；人工生成的对齐只作为兜底。

## D-13 【P2，未验证】线程模型有一处不一致

`DanmakuGuardSession` 中：

- `configInternal` 用 `@Volatile`
- `currentAlignment` 用 `@Volatile`
- `knowledgePack` / `episodeNumberInternal` 用 `synchronized(lock)`

在 `shouldDisplay` 里，三者是**分别读取**的：

```kotlin
val pack = synchronized(lock) { knowledgePack }
val episodeNumber = synchronized(lock) { episodeNumberInternal }
val alignment = currentAlignment          // ← 不在锁内
```

严格说，这三者理论上可以来自**不同次** `startEpisode` 调用。
实际发生的概率极低（需要在切集瞬间恰好有一条弹幕在判定），
但这是一个真实的一致性缺口。

### 建议

把三个字段放进**同一个不可变快照对象**，用一次读取拿到，或统一放进同一把锁。
